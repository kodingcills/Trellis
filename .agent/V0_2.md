# V0.2 — Real-Agent Reuse Campaign

Product question: can a real coding agent reuse validated prior computation
through Trellis across related tasks, reducing recomputation/repository
rediscovery, without reducing task success?

v0.1 is complete and terminal (STATE.json). Do not redesign the runtime
unless real measurements expose a concrete deficiency.

## Phases

1. **Integration (smallest practical)** — DONE 2026-09-15: `crates/trellis-cli`
   (init/status/publish/retrieve/query, JSON out, events ledger, payload pins,

2. **Paired real-agent experiment**: related-task chain on

   --format json --auto`: same model, prompt, tools, CLI, timeout, steps.
   Only difference: A gets a fresh empty store per task (nothing to reuse);
   B's store persists across the chain. Metrics from JSON events + export.
   ≥5 paired trials, alternating condition order. Provider-cached tokens
   recorded separately.
3. **Analyze before more engineering.** Classify dominant limitation from

   smallest intervention → before/after → correctness check; revert if no

5. **Real OSS validation** on a pinned OSS repo (vendored `oss_pip` pin is
   the candidate; no repo-specific shortcuts anywhere).
6. **External validity** (optional second harness) — only after OpenCode
   value is proven.

## Fairness contract

The independent variable is reuse/incremental validity, nothing else. Both
conditions call the same MCP server, same CLI binary, same query
implementation (`trellis query` is always fresh); reuse flows only through
`retrieve`/`publish` + red/green validity. No semantic advantage to B.

## Gates

Primary: task correctness (hidden/public tests) must not regress.
Success: measurable reuse with overhead < work avoided, false-valid stale
reuse 0 (or justified bound), reproduced on OSS repo, reproducible runs.
Kill conditions per campaign brief — report honestly if hit.
